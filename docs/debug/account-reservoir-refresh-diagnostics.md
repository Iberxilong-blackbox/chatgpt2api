# 账号蓄水池自动补水排查记录

## 背景

账号管理页的蓄水池状态出现长期“补水中”，同时显示水位约 `0/200` 或 `24/200`、队列约 `148`、`信息过旧 148`。用户手动刷新单个账号后可以拿到 `25` 图片额度，但自动蓄水池长时间未明显提高水位。

这次排查围绕两个问题展开：

- 为什么顶部账面额度、账号恢复/重置时间和蓄水池水位看起来互相矛盾。
- 为什么自动补水看起来没有成功，以及如何确认每一轮补水到底选了谁、结果如何。

## 现象

### 蓄水池长期显示补水中

页面显示类似：

```text
蓄水池状态：补水中
水位 24 / 200
队列 148
信息过旧 148
到期待刷新 15
```

含义如下：

- `补水中`：后端判断 `currentWater < targetWater`。
- `水位`：蓄水池确认的新鲜可用图片额度，不等于所有账号本地 `quota` 合计。
- `队列`：当前可被蓄水池选择刷新的候选账号数，不是正在执行的后台任务数。
- `信息过旧`：账号曾经验证过，但最近可证明账号额度/状态可信的时间超过默认新鲜度窗口。

### 顶部可用额度与蓄水池水位不一致

顶部原先显示“可用额度 3.0k”，但蓄水池水位只有 `24/200`。原因是两个口径不同：

- 顶部卡片原先按 `status === "正常"` 汇总所有账号的本地 `quota`，不关心信息是否过旧。
- 蓄水池只把新鲜且 `quota > 0` 的账号计入确定水位。

因此顶部的 3.0k 可能是账面旧额度，而蓄水池水位是保守确认额度。

### 恢复时间文案误导

账号字段里的 `restoreAt` 来自 ChatGPT `limits_progress` 中 `image_gen.reset_after`。对于仍有额度的账号，它更像“额度周期重置时间”，不一定表示“当前额度为 0，等待恢复”。

示例：

```json
{
  "feature_name": "image_gen",
  "remaining": 25,
  "reset_after": "2026-07-02T03:59:12.297578+00:00"
}
```

这里 `remaining=25` 表示当前仍有额度，`reset_after` 是下次重置时间。把它统一显示为“恢复时间”会误导判断。

### 明确 0 额度账号仍显示正常

发现部分账号主动刷新后仍是：

```json
{
  "quota": 0,
  "imageQuotaUnknown": false,
  "limits_progress": [],
  "status": "正常",
  "reservoirLayer": "restore_due"
}
```

这说明刷新链路成功更新了部分字段，但状态没有根据明确 0 额度归一化为“限流”。

## 根因分析

### 信息过旧的定义

“信息”指本地缓存的账号状态与额度相关信息，主要包括：

- `status`
- `quota`
- `image_quota_unknown`
- `restore_at`
- `limits_progress`
- `type`

蓄水池通过以下时间字段判断这份信息是否新鲜：

- `quota_checked_at`
- `last_success_at`
- `token_refreshed_at`
- `last_used_at`

默认新鲜度窗口是 `6 小时`。超过窗口后，即使本地仍有 `quota`，蓄水池也不会把它计入确定水位。

### 验证时间取值过于保守

原逻辑按顺序取第一个存在的时间：

```text
quota_checked_at -> last_success_at -> token_refreshed_at
```

如果 `quota_checked_at` 很旧，而 `last_success_at` 或 `token_refreshed_at` 更新，账号仍可能被判为过旧。更合理的行为是取这些证据中的最新时间。

### 自动补水不是没运行，而是缺少可视化

蓄水池自动补水每轮默认最多选 3 个账号。之前界面只显示统计，不显示：

- 本轮选中了哪些账号。
- 为什么选中这些账号。
- 每个账号刷新成功、失败还是成功但额度为 0。
- 失败原因是什么。

因此很难判断是“没轮到”、“被冷却跳过”、“刷新失败”，还是“刷新成功但没有额度”。

### 补水并发可能偏激进

原逻辑中，蓄水池一轮选 3 个账号后复用 `RefreshAccounts()`，而 `RefreshAccounts()` 会按 `min(len(tokens), 10)` 并发刷新。因此一轮补水的 3 个账号会并发请求远端。

为了降低风控和远端压力，蓄水池补水路径改为串行刷新：一轮仍选最多 3 个，但逐个刷新。

## 已完成修改

### 1. 修正验证时间取最新证据

文件：`internal/service/account_reservoir.go`

`accountVerifiedAt()` 改为从 `quota_checked_at`、`last_success_at`、`token_refreshed_at`、`last_used_at` 中取最新时间，避免旧字段压住新字段。

收益：

- 减少误判 `stale_verified`。
- 最近成功使用或 token 刷新过的账号更容易被视为新鲜。

### 2. 顶部额度文案改为账面额度

文件：`web/src/app/accounts/page.tsx`

顶部卡片从“可用额度 / 正常账号合计”改为“账面额度 / 正常账号额度合计”。

收益：

- 明确它是本地账面 `quota` 合计。
- 避免与蓄水池“确定水位”混淆。

### 3. 区分额度重置和恢复时间

文件：`web/src/app/accounts/page.tsx`

账号列表列名改为“重置/恢复时间”。显示规则：

- 限流、过期待刷新、明确 0 额度账号：显示“恢复时间”。
- 正常且有额度账号：显示“额度重置”。

收益：

- 避免把 `reset_after` 一律理解成当前无额度。

### 4. 添加最近一轮调度诊断面板

文件：

- `internal/service/account_reservoir.go`
- `web/src/lib/api.ts`
- `web/src/app/accounts/page.tsx`

蓄水池快照 `lastResult` 增加：

- `manual`：是否手动触发。
- `maintenance`：是否维护刷新。
- `limit`：本轮选择上限。
- `selected`：本轮选中数量。
- `selected_accounts`：选中账号诊断信息。
- `details`：逐账号刷新结果。
- `errors`：逐账号错误。
- `duration_ms`：本轮耗时。

前端新增“最近一轮调度”面板，展示：

- 自动补水 / 手动触发 / 维护刷新。
- 上限、选中、成功、失败、耗时。
- 每个账号的邮箱或用户标识、辅助 token、层级、信息年龄、刷新结果、额度和错误。

收益：

- 可以判断自动补水到底有没有运行。
- 可以区分“没选中”、“刷新失败”、“刷新成功但额度为 0”。

### 5. 添加蓄水池调度日志

文件：`internal/service/account_reservoir.go`

每轮蓄水池调度完成后写入“蓄水池调度”日志，包含：

- 是否手动。
- 是否维护刷新。
- 本轮上限。
- 选中数量。
- 成功/失败数量。
- 耗时。
- 匿名账号信息。
- 错误摘要。

收益：

- 即使不看前端，也可以从日志确认调度行为。

### 6. 0 额度账号状态归一化为限流

文件：`internal/service/account.go`

刷新成功后，如果远端明确返回：

```text
quota == 0
image_quota_unknown == false
```

则状态归一化为“限流”，并增加 0 额度刷新计数。

同时，token 刷新成功后的中间状态也加入保护：如果旧额度仍为 0 且不是未知额度，不强行改回“正常”。

收益：

- 避免 `quota=0` 但 `status=正常` 的矛盾状态。
- 这类账号不会误导顶部状态和后续调度。

### 7. 蓄水池补水改为串行刷新

文件：

- `internal/service/account.go`
- `internal/service/account_reservoir.go`

保留通用 `RefreshAccounts()` 的并发行为，新增：

```go
RefreshAccountsSerial(ctx, tokens)
```

蓄水池补水改为调用串行刷新。现在行为是：

```text
每轮仍最多选 3 个账号
但 3 个账号轮流刷新
远端请求最大并发为 1
```

收益：

- 降低远端请求并发。
- 降低触发风控的概率。
- 不影响手动“刷新选中”、CPA 导入、养号等其它批量刷新流程。

## 如何阅读最近一轮调度面板

### 情况 1：选中 0

```text
选中 0
```

可能原因：

- 没有可刷新候选。
- 候选都处于冷却期。
- 当前水位足够，维护刷新又未到间隔。

### 情况 2：失败大于 0

```text
失败 1 或更多
```

看每张账号卡片的错误。常见原因可能是：

- token 失效。
- session 刷新失败。
- 代理或网络失败。
- Cloudflare / 上游风控。
- 上游接口返回非预期内容。

### 情况 3：成功但额度 0

```text
成功 3
失败 0
每张卡片显示：限流 / 额度 0
```

说明刷新链路本身成功，但远端返回该账号当前没有图片额度。水位不会上涨。

### 情况 4：成功且额度大于 0

```text
成功
正常 / 额度 25
```

说明该账号成功补水，会被计入蓄水池水位。

## 后续建议

### 1. 将蓄水池策略做成配置

当前策略仍是硬编码默认值：

```text
FixedMinWater: 200
StaleAfter: 6h
MaxRefreshPerCycle: 3
MaintenancePerCycle: 1
```

后续可考虑暴露配置项：

- 信息过旧窗口，例如从 6 小时调整为 12 或 24 小时。
- 每轮最大刷新账号数。
- 自动补水周期。
- 是否串行刷新。

### 2. 展示冷却跳过数量

目前队列数量只显示可刷新候选，不直接展示“因为冷却被跳过”的账号数。后续可扩展快照，显示：

- 候选总数。
- 被冷却跳过数量。
- 本轮可选数量。

### 3. 增加账号级刷新历史

如果需要更细排查，可以给每个账号记录最近几次刷新：

- 时间。
- 触发来源：手动 / 蓄水池 / 养号 / CPA。
- 结果。
- 错误。
- 刷新前后 quota/status。

这样能更直观看到某个账号为什么一直不加水。
