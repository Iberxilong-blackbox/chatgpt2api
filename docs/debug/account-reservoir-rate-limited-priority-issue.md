# 蓄水池优先刷新限流账号导致补水效率下降记录

## 背景

在账号数量增长后，蓄水池自动补水经常长期处于“补水中”，但水位提升很慢。最近一轮调度面板显示，补水每轮会选中 3 个账号并刷新成功，但这些账号刷新后仍是：

```text
限流 / 额度 0
```

这说明刷新请求本身成功了，但本轮补水并没有带来新的可用额度。

## 关键现象

### 1. 补水槽位经常被限流账号占用

当前蓄水池调度优先级里，`restore_due` 是最高优先级：

```text
restore_due: 500
unverified_imported: 400
long_unrefreshed: 300
stale_verified: 200
available_unknown_quota: 100
```

而部分限流账号会被归类为 `restore_due`，因此会优先于大量 `信息过旧` 账号被刷新。

### 2. 每轮补水数量有限

当前一轮补水最多选 3 个账号。后续已改为串行刷新，但一轮仍然只有 3 个补水槽位。

如果这 3 个槽位长期被“刷新后仍然 0 额度”的限流账号占用，那么蓄水池就很难轮到那些可能实际有额度、但只是信息过旧的账号。

### 3. 5 分钟冷却不足以解决问题

当前有短期冷却：

```text
同一个 token 最近刷新过后，5 分钟内不会再次被选中。
```

这个冷却只能防止同一个账号在短时间内连续刷新，但当账号池里有大量限流账号时，调度器会在这些限流账号之间轮转。

结果是：

```text
不是同一个限流账号反复刷，
而是一批限流账号轮流占用补水槽位。
```

因此从整体看，补水仍然经常浪费在无法加水的账号上。

## 当前分类逻辑的问题

当前限流账号大致分两类：

### 有未来 restore_at 的限流账号

如果 `status == "限流"` 且 `restore_at` 在未来，会归类为：

```text
empty_waiting_restore
```

这类账号不会进入刷新候选队列。这个逻辑是合理的。

### restore_at 为空、解析失败或已经到期的限流账号

如果 `status == "限流"`，但没有有效的未来 `restore_at`，当前会归类为：

```text
restore_due
```

它会拿到最高优先级 `500`。

问题主要出在这里：

- 有些账号主动刷新后仍然 `quota=0`。
- 有些账号远端返回 `limits_progress=[]`，没有 `restore_at`。
- 这类账号会不断被视为“到期待刷新”。
- 因为优先级最高，它们会抢在 `信息过旧` 账号前面。

## 具体问题案例

曾观察到类似账号：

```json
{
  "email": "raytimothy@zainy.art",
  "imageQuotaUnknown": false,
  "limits_progress": [],
  "quota": 0,
  "quotaCheckedAt": null,
  "restoreAt": null,
  "status": "正常",
  "tokenRefreshedAt": "2026-07-01T12:32:31.054537584Z",
  "type": "Free",
  "zeroQuotaRefreshCount": 0
}
```

后续已修复明确 0 额度账号仍显示“正常”的问题：刷新成功后如果 `quota=0 && image_quota_unknown=false`，会归一化为“限流”。

但状态归一化后，这类账号仍可能因为 `restore_at=null` 被归为 `restore_due`，继续优先占用补水槽位。

## 为什么这会导致水池补不满

蓄水池目标是提高 `currentWater`，也就是确认新鲜且有额度的账号水位。

但当前排序会让补水流程优先处理：

```text
限流且到期待刷新 / 无恢复时间账号
```

这些账号刷新成功后经常仍然是：

```text
quota = 0
status = 限流
```

因此：

- 刷新成功数量看起来正常。
- 失败数可能是 0。
- 但水位没有上涨。
- 信息过旧但可能有额度的账号迟迟轮不到。

这就是“补水在运行，但水池补不满”的核心原因之一。

## 已有保护及其不足

### 已有保护：5 分钟刷新冷却

`lastRefreshAttempt` 会阻止同一 token 在 5 分钟内重复进入候选。

不足：

- 只能保护单个账号。
- 对大量限流账号轮流占用补水槽位无效。

### 已有保护：连续 0 额度计数

当前有字段：

```text
zero_quota_refresh_count
ZeroQuotaMaxRechecks = 2
```

当账号连续刷新出 0 额度达到阈值后，会进入：

```text
zero_quota_rechecked
```

不足：

- 在达到阈值前，这类账号仍可能以最高优先级参与调度。
- 如果账号很多，补水仍会被大量 0 额度账号消耗。
- 部分历史账号可能计数字段不完整，导致还要多轮确认。

## 建议修复方向

### 方案 A：降低无 restore_at 的限流账号优先级

将：

```text
status = 限流
quota = 0
restore_at = null
```

从最高优先级 `restore_due` 中移出，改为低优先级层级，例如：

```text
zero_quota_recheck_due
```

优先级应低于 `stale_verified`，避免抢占可能有额度的信息过旧账号。

建议排序：

```text
restore_due             500  仅 restore_at 已到期或过期待刷新
unverified_imported     400
long_unrefreshed        300
stale_verified          200
available_unknown_quota 100
zero_quota_recheck_due   50  无恢复时间的 0 额度账号低频重查
```

### 方案 B：对无 restore_at 的 0 额度账号设置更长冷却

例如：

```text
普通刷新冷却：5 分钟
0 额度无恢复时间冷却：6 小时或 24 小时
```

这样可以保留低频重查能力，但不会持续抢占补水槽位。

### 方案 C：连续 0 额度后直接退出补水候选

如果账号连续刷新出 0 额度达到阈值：

```text
zero_quota_refresh_count >= 2
```

则进入 `zero_quota_rechecked`，不再参与补水候选，只能手动刷新或等待后续策略恢复。

当前已有这个层级，但建议配合方案 A/B，让达到阈值前也不要高优先级抢占。

### 方案 D：补水优先处理信息过旧有账面额度账号

对于 `stale_verified` 且 `quota > 0` 的账号，补水价值通常高于无恢复时间的 0 额度账号。

建议在缺水状态下优先级上调或至少排在 `zero_quota_recheck_due` 前面。

## 推荐实现顺序

1. 新增低优先级层级：`zero_quota_recheck_due`。
2. 修改分类逻辑：限流且无有效 `restore_at` 的 0 额度账号进入该层级，而不是 `restore_due`。
3. 设置该层级优先级低于 `stale_verified`。
4. 保留 `restore_at` 已到期账号的 `restore_due` 高优先级。
5. 可选：给该层级增加更长冷却窗口。
6. 前端增加层级文案，例如“0额度待低频复查”。

## 后续观察指标

修复后重点观察最近一轮调度面板：

- 是否还长期优先选择 `到期待刷新` 且刷新后 `额度 0` 的账号。
- `信息过旧` 账号是否开始被选中刷新。
- 水位是否随着 stale 账号刷新成功而上涨。
- `zero_quota_rechecked` 数量是否逐渐沉淀出无补水价值账号。

## 当前结论

当前蓄水池不是完全没有运行，而是补水优先级会让大量限流、无恢复时间或刷新后仍 0 额度的账号优先消耗补水轮次。5 分钟冷却只能防止同一个账号短时间重复刷新，无法防止一批限流账号轮流占用补水槽位。

这个问题应作为独立调度策略问题处理，重点是降低无恢复时间 0 额度账号的补水优先级，并让可能有额度的 `信息过旧` 账号更早得到刷新机会。
