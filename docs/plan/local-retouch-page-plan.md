# 局部修图专用页面开发计划

> 目标：在不改动现有图片任务主链路的前提下，新增一个面向高频 P 图场景的专用页面，让用户上传图片、标注修改区域、输入修改诉求，并自动构造高一致性局部编辑 prompt 后提交到现有图片编辑任务。
> 计划日期：2026-06-25

## 背景

当前项目的核心使用入口是创作台。实际使用中，“基于原图局部 P 图”的场景频率很高，典型流程是：

1. 用户准备一张原图。
2. 用户用红框、红圈或其他可见标记指出需要修改的区域。
3. 用户输入局部修改要求。
4. 系统把标注图和 prompt 一起发给图片编辑 API。

现有手工 prompt 通常强调：

- 参考输入图像。
- 只修改标注区域。
- 未标注区域保持不变。
- 修改内容与原图光照、透视、风格一致。
- 边缘自然融合。

这个流程有效，但每次都需要用户自己标注图片并手写长 prompt，操作成本高。因此本轮计划把它收敛成一个专用页面。

## 当前代码基础

可复用能力：

- 图片编辑任务提交已存在：`web/src/lib/api.ts` 中的 `createImageEditTask`。
- 创作任务接口已存在：`/api/creation-tasks/image-edits`。
- 图片任务队列、任务轮询、结果保存、图片库入库逻辑已由创作台链路承担。
- `createImageEditTask` 已预留 `input_image_mask` 参数，但第一版暂不依赖 mask。

本轮不重写图片任务系统，也不新建独立后端任务模型。新增页面只作为更适合局部修图的前端工作流入口。

## 目标

1. 新增一个局部修图专用页面，例如 `/retouch` 或 `/image-retouch`。
2. 用户可以上传单张图片作为原图。
3. 用户可以在图片上直接标注需要修改的区域。
4. 页面根据标注区域背景自动选择高对比度标注颜色；如果红色满足高对比要求，默认优先使用红色。
5. 用户只输入“想怎么改”，系统自动拼接完整局部编辑 prompt。
6. 提交时复用现有 `createImageEditTask` 和 `/api/creation-tasks/image-edits`。
7. 结果继续进入现有图片任务队列和图片库，不重复实现任务存储、轮询和管理。
8. 图片保存、参考图处理、可见性等行为与创作台保持一致。

## 非目标

1. 第一版不实现上游 mask 协议改造。
2. 第一版不新增后端数据库表、任务类型或存储策略。
3. 第一版不做复杂图层系统、路径对象编辑、套索选区、多图拼接。
4. 第一版不承诺模型能 100% 保持未标注区域完全不变，只通过 prompt 和标注图尽量约束。
5. 第一版不实现“结果继续编辑”的完整多轮链路，该能力纳入 1.1。
6. 第一版不引入兼容旧 API 的 fallback，按当前项目规则只面向当前接口实现。

## 核心产品流程

### 1. 上传原图

用户进入页面后，先上传一张图片。

要求：

- 仅接受 `image/*`。
- 显示图片预览。
- 保留原始图片文件，用于提交图片编辑任务。
- 生成前端 object URL 或 data URL 供 canvas 绘制。

### 2. 标注区域

第一版推荐使用“涂鸦式标注”，但工程实现应保持克制：

- 提供画笔。
- 提供撤销。
- 提供清空。
- 提供笔刷大小。
- 支持鼠标和触控。

如果完整自由涂鸦实现成本过高，可采用工程折中方案：

- 使用连续点采样绘制平滑线条。
- 不保存复杂矢量路径编辑能力。
- 每次落笔结束保存一份 raster 快照用于撤销。
- 不支持拖拽修改已画线条。

这能达到用户感知上的“自己涂鸦圈选区域”，同时避免引入过重编辑器。

### 3. 动态标注颜色

问题：固定红框在红色、橙色、粉色背景上对比度不足。

第一版使用有限候选色评分算法：

1. 在用户标注路径附近采样原图像素。
2. 计算局部背景平均亮度和颜色。
3. 判断红色是否达到高对比阈值。
4. 如果红色可用，优先使用红色。
5. 如果红色不可用，再从候选色中选择对比度最高的颜色。
6. 绘制时使用“双描边”增强可见性。

候选色建议：

- cyan
- yellow
- magenta
- red
- blue
- green
- white
- black

颜色优先级：

- 红色满足高对比阈值时，默认使用红色。
- 多个非红色候选色都满足阈值时，选择对比度最高的颜色。
- 所有候选色都接近阈值时，仍选择对比度最高者，并依赖双描边提高可见性。

双描边规则：

- 外层使用黑色或白色，取决于背景亮度。
- 内层使用算法选出的高对比颜色。

这样比任意生成颜色更可控，也保留用户熟悉的红色标注习惯；只有红色对比不足时才切换为其他高对比颜色。

### 4. 构造标注图

提交前，前端生成一张合成图：

- 底图为用户上传的原图。
- 上层为动态颜色绘制的标注线条。
- 输出为 PNG 或与创作台兼容的图片文件。

第一版将这张标注图作为 `createImageEditTask` 的输入图片。

原因：

- 与当前已验证的“用户手动红框 + prompt”模式一致。
- 不依赖上游 mask 参数是否稳定。
- 不需要后端新增协议。

### 5. 构造 prompt

用户只填写局部修改要求。系统自动拼接完整 prompt。

模板建议：

```text
参考输入图像，用户已用高对比度的<标注颜色中文名>涂鸦/框线标出需要修改的区域。

仅对标注区域进行编辑，其余图像内容必须保持不变，包括人物、背景、光影、构图、色彩一致性。

在标注区域内：
<用户输入>

要求：
- 修改后的内容必须与原图光照、透视、风格一致
- 边缘自然融合，无拼接感
- 不改变未标注区域的细节
- 保持整体画面真实一致性；如果原图是动漫或插画，则匹配原图风格

high consistency, seamless blending, matching original style
```

注意事项：

- 不再固定写“红色矩形框/红色圆圈”。
- 根据实际标注颜色写入颜色名。
- 如果采用涂鸦，不要强制写“矩形框/圆圈”，避免 prompt 与图像不一致。
- 用户输入为空时不允许提交。

## 页面结构计划

页面建议采用三段式工具布局：

1. 左侧或主区域：图片标注画布。
2. 右侧操作栏：上传、画笔、撤销、清空、笔刷大小、标注颜色状态。
3. 底部或右侧输入区：用户修改要求、生成数量、模型/尺寸等必要参数、提交按钮。

设计原则：

- 这是高频工具页面，不做营销式 hero。
- 优先保证画布面积、控件可发现性和重复操作效率。
- 控件复用现有 shadcn-style primitives 和创作台视觉语言。
- 不新增复杂说明文字，必要提示放在按钮 tooltip 或简短帮助文案里。

## 前端实现计划

### 1. 新增路由页面

建议文件：

- `web/src/app/retouch/page.tsx`

或如果希望与图片模块更贴近：

- `web/src/app/image-retouch/page.tsx`

同时在 `web/src/components/top-nav.tsx` 增加导航项，例如“局部修图”。

### 2. 抽取标注画布组件

建议新增：

- `web/src/app/retouch/components/retouch-canvas.tsx`

职责：

- 加载并绘制原图。
- 处理 pointer events。
- 绘制标注线条。
- 管理笔刷大小、撤销、清空。
- 导出合成标注图 `File`。

原则：

- SRP：画布组件只负责标注交互和图片导出。
- 不直接提交任务，避免 UI 绘制与业务请求耦合。

### 3. 新增 prompt 构造 helper

建议新增：

- `web/src/app/retouch/retouch-prompt.ts`

职责：

- 根据用户输入、颜色名、标注方式构造最终 prompt。
- 保持模板集中维护，避免页面和测试中重复字符串。

原则：

- DRY：prompt 模板只维护一份。
- KISS：第一版只支持一个清晰模板，不做模板市场或多模式配置。

### 4. 复用图片编辑任务提交

页面提交时：

1. 调用画布组件导出标注图文件。
2. 调用 `buildRetouchPrompt(userPrompt, markerColorName)`。
3. 调用现有 `createImageEditTask`。
4. 使用现有任务状态展示或轻量复用创作台任务轮询逻辑。

如果创作台当前轮询逻辑强耦合在 `web/src/app/image/page.tsx`，第一版可先实现页面内最小轮询，但应避免复制大量复杂状态。必要时后续再把任务轮询抽成 shared hook。

### 5. 权限和访问控制

第一版页面权限与创作台保持一致。

需要核对：

- 登录态守卫是否可复用 `useAuthGuard`。
- 当前 RBAC 菜单是否需要新增 `/retouch` 路径。
- 普通用户如果能使用创作台图片编辑，也应能使用局部修图页。

## 后端实现计划

第一版原则上不需要新增后端能力。

只在以下情况做最小改动：

1. 如果菜单权限系统需要登记 `/retouch` 路径，则补充权限/菜单配置。
2. 如果现有任务队列组件只识别 `/image`，需要调整为可在新页面展示同一任务队列。
3. 如果任务提交要求 `frontend_conversation_id`，新页面可生成独立前端会话 ID，但不新增后端字段。

不做：

- 不新增 `/api/creation-tasks/retouch`。
- 不新增 `mode=retouch`。
- 不新增图片存储策略。

## 1.1 计划：结果继续编辑

用户确认某张结果可继续修改时，提供“继续编辑”入口：

1. 将生成结果作为新原图加载到局部修图页。
2. 清空上一轮标注。
3. 保留或重置上一轮参数。
4. 用户重新标注并提交。

实现建议：

- 可先通过 URL state、localStorage 或现有图片库意图机制传递图片 URL。
- 如果结果图片需要鉴权访问，复用现有 `AuthenticatedImage` / authenticated image cache 逻辑。
- 不把多轮编辑设计成独立会话树，避免第一阶段复杂化。

## 后续增强：mask 模式

现有 `createImageEditTask` 已支持 `inputImageMask` 参数。后续可在确认上游协议稳定后增强为：

1. 前端导出原图文件。
2. 前端导出二值 mask。
3. 前端可选导出标注预览图。
4. 提交时传 `input_image_mask`。

引入 mask 前需要验证：

- 上游当前是否稳定接受 mask。
- mask 尺寸、透明通道、黑白语义要求。
- 多参考图与 mask 同时存在时的行为。
- SSE 事件和任务结果格式是否变化。

如果需要验证 ChatGPT Web 行为，应按项目规则使用 `jshook` 新鲜捕获，不仅依赖旧文档。

## 风险与应对

### 风险 1：模型把标注线当成画面内容

应对：

- prompt 明确说明标注只是修改区域提示。
- 标注线尽量使用边界或半透明高对比线。
- 后续 mask 模式解决精细区域问题。

### 风险 2：自由涂鸦实现过重

应对：

- 第一版采用 raster 快照撤销，不做矢量路径编辑。
- 只保留画笔、撤销、清空、笔刷大小。

### 风险 3：任务轮询逻辑重复

应对：

- 优先复用现有任务队列组件。
- 如果页面内必须轮询，先保持最小实现，后续抽 `useCreationTaskPolling`。

### 风险 4：权限菜单遗漏

应对：

- 新页面权限与创作台一致。
- 新增路由后同步检查 top nav、RBAC 菜单、登录重定向。

## 原则落地

- **KISS**：第一版只做“上传原图、标注、拼 prompt、提交图片编辑任务”，不引入复杂图层、mask 协议和新任务类型。
- **YAGNI**：暂不做模板市场、多轮会话树、自动局部合成、复杂路径编辑等未来能力。
- **DRY**：复用 `createImageEditTask`、现有图片任务队列、图片库保存策略和 UI primitives；prompt 模板集中在一个 helper 中。
- **SOLID / SRP**：画布组件负责标注，prompt helper 负责文本构造，页面负责状态编排，API helper 负责任务提交。
- **OCP**：后续添加 mask 模式或“继续编辑”时，可以扩展提交参数和页面入口，不需要修改现有图片编辑接口语义。
