# 前端页面开发流程 Guide

本文档用于规范后续前端页面、复杂交互界面和 UI 重构工作的推进方式。目标是把“脑海中的交互想法”转换为可讨论、可评审、可实现、可验证的开发规格，避免直接凭感觉改 UI 导致状态遗漏、接口时机不清、返工成本过高。

适用场景：

- 新建一个前端页面或工具型界面。
- 重构已有页面的布局、交互和状态流。
- 将 mock 原型接入真实 API。
- 需要分阶段推进复杂交互，例如上传、涂鸦、提交、轮询、对比、历史、分支等流程。

核心原则：

- **KISS**：先定义主路径，先把核心状态跑通，再补充边缘交互。
- **YAGNI**：只实现当前阶段明确需要的状态和按钮，不提前堆复杂能力。
- **DRY**：重复出现的交互规则、状态字段、API 轮询逻辑应沉淀为可复用 helper 或 store action。
- **SOLID**：页面负责编排，组件负责展示，store 负责状态，API helper 负责请求，避免一个组件承担所有职责。

## 1. 产品目标

产品目标用于回答“这个页面到底要解决什么问题”，不要一开始就描述按钮、颜色和布局。

建议写清楚：

- 用户是谁。
- 用户进入这个页面时想完成什么任务。
- 这个页面最核心的成功结果是什么。
- 当前阶段不做什么。
- 这个页面和现有系统中的其他页面有什么关系。

模板：

```text
页面名称：

目标用户：

核心任务：

成功标准：

当前阶段范围：

暂不实现：

依赖页面/模块：
```

示例：

```text
页面名称：局部重绘 Retouch 页面

目标用户：需要对已有图片做局部修改的图片生成用户。

核心任务：上传图片，圈选需要修改的区域，输入修改指令，提交生成任务，并查看原图与生成图的对比结果。

成功标准：用户可以完成“上传 → 涂鸦 → 输入指令 → 提交 → 查看结果”这一条主路径。

当前阶段范围：只实现单张图片、单次生成、成功后左右对比。

暂不实现：复杂分支小地图、批量生成、多结果选择、多人协作。

依赖页面/模块：RetouchCanvas、creation-tasks API、图片任务轮询逻辑。
```

## 2. 核心用户路径

核心用户路径描述用户从进入页面到完成任务的主流程。这里先不追求完整 UI 细节，而是把动作顺序和状态变化讲清楚。

要求：

- 使用线性步骤表达主路径。
- 每一步都包含用户动作和系统响应。
- 明确哪些步骤会触发 API。
- 不把异常路径混进主路径，异常路径放到第 7 节。

模板：

```text
1. 用户进入页面。
   系统显示：

2. 用户执行：
   系统响应：

3. 用户执行：
   系统响应：

最终结果：
```

示例：

```text
1. 用户进入 Retouch 页面。
   系统显示空态上传区域和禁用的底部输入框。

2. 用户上传一张图片。
   系统显示图片编辑画布、涂鸦工具和可输入的底部指令框。

3. 用户在图片上圈选需要修改的区域。
   系统保留涂鸦标记，并允许用户继续调整。

4. 用户输入 prompt 并点击发送。
   系统导出标记图或 mask，提交图片编辑任务，进入 loading 状态。

5. API 返回生成结果。
   系统展示左右对比：左侧为本次基底图，右侧为生成图。

最终结果：用户可以清晰比较修改前后图片，并决定是否继续编辑。
```

## 3. 页面状态表

页面状态表是复杂 UI 的核心。它把“页面看起来怎么样”拆成稳定状态，避免开发时只靠多个 boolean 拼凑。

要求：

- 每个状态必须有清晰名称。
- 每个状态说明进入条件、显示内容、可执行操作、禁用操作、下一状态。
- 状态数量保持克制，避免为每个微小变化都新增状态。
- 如果状态开始变复杂，优先考虑用 `mode`、`status` 或状态机式结构，而不是堆叠多个互相冲突的 boolean。

模板：

```text
状态名：
进入条件：
主区域：
底部/侧边控制区：
允许操作：
禁用操作：
API 行为：
下一状态：
```

推荐表格格式：

| 状态 | 进入条件 | 主区域 UI | 控制区 UI | 允许操作 | 下一状态 |
| --- | --- | --- | --- | --- | --- |
| `empty` | 无图片 | 上传区 | 输入禁用 | 上传图片 | `editing` |
| `editing` | 已有图片 | 图片画布和涂鸦层 | 输入可用 | 涂鸦、发送、移除 | `submitting` |
| `submitting` | 点击发送 | 保持当前图片与标记 | 输入禁用、按钮 loading | 等待、取消 | `polling` / `error` |
| `polling` | 任务已创建 | 显示生成中反馈 | 输入禁用 | 取消 | `success` / `error` |
| `success` | 生成成功 | 左右对比 | 输入可用或显示继续编辑入口 | 继续编辑、回看历史 | `editing` / `history` |
| `error` | 提交或生成失败 | 保留原图与标记 | 显示错误和重试 | 重试、修改 prompt、取消 | `submitting` / `editing` |

## 4. 每个状态的 UI 布局

这一节把状态表翻译成页面结构。它不只是视觉描述，还要说明布局容器、响应式策略、主要组件和空白区域如何处理。

要求：

- 每个状态至少描述主区域、控制区域、反馈区域。
- 明确哪些元素固定、哪些元素随内容变化。
- 对全屏工具型页面，优先说明高度、滚动和溢出策略。
- 关键状态建议配 Figma frame、截图或 ASCII 草图。

模板：

```text
状态：

布局目标：

主区域：

控制区：

反馈区：

响应式：

滚动/溢出：

设计注意：
```

示例：

```text
状态：success

布局目标：
让用户快速比较修改前后差异。

主区域：
使用双列布局，左侧显示基底图，右侧显示生成图。两张图保持相同视觉权重。

控制区：
底部输入框保留，用于继续输入下一轮编辑指令。发送按钮恢复可用。

反馈区：
生成图上方显示任务状态、尺寸或必要的结果信息，但不遮挡主体图像。

响应式：
桌面端左右并列，窄屏可改为上下堆叠。

滚动/溢出：
工具页面默认锁定在视口内，不出现页面级滚动条。长内容只允许局部滚动。

设计注意：
不要把说明文字堆在主图上。操作按钮尽量图标化，并提供 aria-label。
```

## 5. 每个按钮/手势的行为

这一节定义交互契约。每个按钮、快捷操作、拖拽、滚轮、键盘行为都要明确触发条件和结果。

要求：

- 每个交互都写明 enabled/disabled 条件。
- 写清楚点击后是否立即改变 UI 状态。
- 写清楚是否触发 API、是否需要防重复提交。
- 手势类交互要说明节流、防误触和默认浏览器行为。

模板：

```text
交互名称：
触发方式：
可用条件：
禁用条件：
立即 UI 反馈：
状态变化：
API 行为：
失败处理：
无障碍要求：
```

示例：

```text
交互名称：发送编辑指令

触发方式：
点击发送按钮，或在输入框内按 Enter。

可用条件：
已有当前图片、prompt 非空、不处于 submitting/polling。

禁用条件：
无图片、prompt 为空、任务正在进行。

立即 UI 反馈：
发送按钮变为 loading，输入框禁用，画布保留当前标记。

状态变化：
`editing` → `submitting`。

API 行为：
导出当前图片和 mask，调用图片编辑任务 API。

失败处理：
进入 `error` 状态，保留用户输入和标记，允许重试。

无障碍要求：
纯图标发送按钮必须提供 `aria-label="发送指令"`。
```

## 6. API 调用时机

API 调用时机用于明确“什么时候调接口、调哪个接口、传什么、结果如何进入 UI”。这能避免 mock UI 和真实后端接入脱节。

要求：

- 每个 API 调用都绑定到一个明确的状态转换。
- 请求参数来自哪里要写清楚。
- 返回数据如何映射到前端状态要写清楚。
- 轮询、取消、重试要有统一策略。
- 不在展示组件里直接散落请求逻辑，优先通过 API helper 或 service 层调用。

模板：

```text
API 名称：
触发状态/交互：
请求方法与路径：
请求参数：
成功响应：
前端状态写入：
失败响应：
重试策略：
取消策略：
```

示例：

```text
API 名称：创建图片编辑任务

触发状态/交互：
`editing` 状态下点击发送。

请求方法与路径：
POST /api/creation-tasks/image-edits

请求参数：
- client_task_id
- image
- prompt
- input_image_mask（仅有涂鸦时传真正 mask data URL）
- model
- size
- visibility

成功响应：
返回 CreationTask，通常状态为 queued 或 running。

前端状态写入：
记录 taskId，将页面状态切到 `polling`。

失败响应：
显示错误信息，状态切到 `error`。

重试策略：
保留 prompt 和标记，用户点击重试时重新提交。

取消策略：
调用取消任务 API，成功后回到 `editing` 或 `cancelled` 状态。
```

## 7. 错误、取消、重试

异常流程需要单独设计，不能等实现时临时补。好的错误处理会尽量保留用户工作成果，避免用户重新上传、重新涂鸦、重新输入。

要求：

- 错误信息要面向用户可理解，不直接暴露底层堆栈。
- 可恢复错误必须提供重试路径。
- 取消后要明确保留什么、清除什么。
- 超时和网络错误要有单独策略。
- 不要因为失败清空用户输入、涂鸦和当前图片。

模板：

```text
错误类型：
出现时机：
用户可见反馈：
保留数据：
清除数据：
可执行操作：
下一状态：
```

推荐错误类型：

| 错误类型 | 出现时机 | 反馈 | 保留数据 | 操作 |
| --- | --- | --- | --- | --- |
| 上传失败 | 选择文件后 | 文件格式或读取失败提示 | 无 | 重新选择 |
| 导出 mask 失败 | 点击发送后 | 标记导出失败提示 | 图片、prompt | 重试或清除标记 |
| 提交失败 | 创建任务 API 失败 | 提交失败提示 | 图片、标记、prompt | 重试 |
| 生成失败 | 任务返回 error | 生成失败原因 | 图片、prompt、历史 | 重试或修改 prompt |
| 任务超时 | 轮询超过限制 | 超时提示 | taskId、图片、prompt | 继续等待、取消、重试 |
| 用户取消 | 点击取消 | 任务已取消 | 图片、prompt 可选保留 | 继续编辑 |

## 8. 第一阶段实现范围

第一阶段实现范围用于防止一次性开发过大。每次迭代都应该有明确验收标准，完成后再进入下一阶段。

要求：

- 只选择一条最关键主路径。
- 明确本阶段做什么、不做什么。
- 明确验收方式。
- 明确需要更新的代码范围。
- 明确需要运行的验证命令。

模板：

```text
阶段名称：

本阶段目标：

包含范围：

不包含范围：

涉及文件/模块：

验收标准：

验证命令：

后续阶段：
```

示例：

```text
阶段名称：Retouch 主路径真实 API 接入

本阶段目标：
把现有 mock 生成流程替换为真实图片编辑任务调用。

包含范围：
- 上传图片后进入涂鸦态。
- 输入 prompt 后点击发送。
- 导出标记数据。
- 调用创建图片编辑任务 API。
- 轮询任务结果。
- 成功后展示左右对比。
- 失败后保留图片、prompt 和标记，允许重试。

不包含范围：
- 分支小地图。
- 多结果选择。
- 批量任务。
- 复杂历史编辑。

涉及文件/模块：
- web/src/pages/EditorPage.tsx
- web/src/store/useImageTreeStore.ts
- web/src/lib/api.ts
- web/src/app/retouch/components/retouch-canvas.tsx

验收标准：
- DevTools Network 中能看到真实 `/api/creation-tasks/image-edits` 请求。
- 成功返回后右侧显示真实生成图，而不是 mock 图片。
- 提交中按钮 loading 且不能重复提交。
- 失败时不清空用户工作内容。

验证命令：
- cd web && npm run build
- cd web && npm run lint

后续阶段：
- 继续编辑生成图。
- 历史层叠导航。
- 分支小地图。
```

## 推荐工作流

后续每个前端页面迭代建议按以下顺序推进：

1. 先写本 guide 中的 8 个章节，不直接改代码。
2. 评审主路径和状态表，确认没有明显状态遗漏。
3. 只实现第一阶段范围。
4. 启动本地页面，用截图或人工操作逐状态验收。
5. 接入真实 API 后检查 Network、loading、error、retry。
6. 通过 build/lint 后，再进入下一阶段。

这套流程的重点不是增加文档负担，而是把 UI 想法提前结构化。只要主路径、状态表、交互行为和 API 时机写清楚，后续实现就能更小步、更可控，也更容易发现设计中的矛盾。
